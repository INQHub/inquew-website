# Video intake pipeline: production debugging session

_Continues from chat2.md (build-out, deployment, admin expansion). This session fixed the live video-intake flow, which was completely broken for real customers. Written as a handoff for whichever Claude session picks this up next._

---

## What was broken, and what actually fixed it

Kenny reported the intake flow crashing with `Unexpected token 'R', "Request En"... is not valid JSON` as soon as he tried it live. That kicked off a long chain of fixes, most of which were real, defensible engineering improvements — but the actual root cause at the very end turned out to be much simpler than any of them. In order:

1. **The original crash** — a full ~2-minute recording exceeded Vercel's ~4.5MB serverless request-body limit. Vercel rejected it at the platform level with a plain-text `413`, and the client crashed trying to `JSON.parse()` that. **Real fix**: recordings now upload straight from the browser to Supabase Storage via a signed URL (`/api/intake/[id]/upload-url`, `lib/supabase-browser.ts`), bypassing Vercel's function body entirely. This was necessary and is still exactly right.
2. **Next symptom**: clean "Transcription failed" JSON (no more crash), but transcription itself failed. Added `maxDuration = 60/30` to the transcribe/statements routes on the theory it was a function-timeout issue. Reasonable, kept it, but it wasn't the actual cause here.
3. **Next symptom**: `Connection error.` from the OpenAI SDK, unchanged by a Hobby→Pro Vercel upgrade. Trimmed `.trim()` on both API keys (guards against a pasted trailing newline/space) — good defensive change, kept it, but not the cause here either.
4. **Next symptom**: same error, now with the underlying cause surfaced (`err.cause`) — `ECONNRESET ... read ECONNRESET` talking to `api.openai.com/v1/audio/transcriptions`. Theorized the video (not just audio) was blowing past Whisper's 25MB cap and getting reset. Built real audio-only extraction: the browser now runs a second `MediaRecorder` on just the audio track (`app/(public)/intake/page.tsx`), sends that small clip to `/transcribe`, and separately archives the full video to storage via `videoPath`. This is a genuinely good change — smaller, faster, more reliable regardless — but it did **not** fix the error.
5. **Same error again**, byte-identical, after the audio-only change. Theorized a stale pooled keep-alive connection (a known class of issue for serverless→external-API calls) and disabled `keepAlive` on both SDK clients' `httpAgent` (`lib/ai.ts`). Also did not fix it.
6. **The actual root cause**: Kenny's OpenAI project (`Inquew_Transcriptions_...`) had **no billing/credits configured**. `platform.openai.com` → Usage showed 0 requests, 0 spend, and a persistent "Add credits to run your next API request" banner. OpenAI's infrastructure apparently rejects unfunded-project requests by resetting the connection rather than returning a clean 402/429 — which is why every single one of steps 2–5 looked plausible and changed nothing. **Once Kenny added a payment method and credits, it worked immediately**, no code change needed for the actual fix.

**Takeaway for next time**: if `OPENAI_API_KEY` (or presumably any paid API key) starts throwing raw connection errors with no application-level error message, check the provider's billing/credits page *before* chasing network-layer theories. It's a five-second check that would have skipped steps 2–5 entirely.

## New sandbox-specific notes (in addition to chat2's)

- **This sandbox cannot reach OpenAI, Anthropic, Stripe, Supabase, or Vercel APIs directly** — same as chat2 already said, but this session re-confirmed it specifically for OpenAI: a local test with a dummy `OPENAI_API_KEY` reached the real `transcribeVideo()` call and got `403 Host not in allowlist: api.openai.com` from the sandbox's own network proxy. That's expected sandbox behavior, not a bug — don't chase it.
- **Two local clones existed simultaneously this session**: `/home/claude/inqhub/inquew-website` (read-only, from the anonymous public-repo git proxy) and `/home/claude/inquew-website` (push-authorized, from `add_repo` with `access: "push"`). The read-only one was cloned first before realizing push access was needed; commits made there had to be exported as a patch (`git format-patch` / `git am`) and replayed onto the push-authorized clone. If starting fresh, call `add_repo` with `access: "push"` up front if any pushing is anticipated, to avoid this dance.
- **Playwright with `--use-fake-device-for-media-stream --use-fake-ui-for-media-stream` Chromium flags + `context.grantPermissions(["camera", "microphone"])`** successfully drives the real `getUserMedia`/`MediaRecorder` flow locally, including the new dual-recorder (video + audio-only) logic — useful for testing the intake recording flow without a real camera. The button `getByRole("button", { name: "Stop and submit" })` can be flaky right after `getByRole("button", { name: "Start recording" }).click()`; wait for `text=Stop and submit` to appear first, then use a `locator("button", { hasText: ... })` click.
- **Local Postgres cluster needs `sudo pg_ctlcluster 16 main start` fresh each new sandbox session** — it's not running by default even though the `inquew_dev` database/data persists on disk.
